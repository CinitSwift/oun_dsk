# Oun Electron 桌面打包设计

## 1. 目标与范围

将现有 Oun 视频聚合网站打包为 macOS 和 Windows 桌面应用。应用内置 React/Vite 前端和本地代理服务，安装后不要求用户另行安装 Node.js、pnpm 或 Docker；搜索、视频源请求和媒体播放仍需要网络连接。

第一版包含：

- Electron 桌面窗口。
- 随应用启动和退出的本地代理服务。
- macOS 和 Windows 安装包。
- 系统托盘入口。
- 关闭窗口时隐藏到托盘。
- 单实例启动。
- HLS/MP4 播放、搜索、视频源导入、历史记录等现有功能回归验证。

第一版不包含：

- 自动更新。
- 开机启动。
- 登录状态同步。
- 原生下载器。
- 离线视频缓存。
- Linux 安装包。
- DRM 绕过或其他改变视频源访问限制的能力。

## 2. 当前项目约束

现有项目位于 `web/oun/`，技术栈为 React 19、Vite 6 和 TypeScript，使用 pnpm 管理依赖。生产构建输出到 `dist`。视频播放使用 Artplayer 和 `hls.js`，网络请求依赖现有 Express 代理 `proxy-server.js`，前端请求路径主要为 `/proxy?url=...`。

桌面化不能只把 `dist` 装进 Electron：本地代理也必须随应用分发并由 Electron 管理，否则安装后的用户环境没有 Node.js 来运行代理服务。

## 3. 方案选择

采用 Electron + electron-builder。

### 3.1 备选方案

#### Electron + electron-builder

Electron 主进程负责窗口、托盘和代理生命周期，`electron-builder` 负责生成 macOS `.dmg` 和 Windows `.exe` 安装包。它可以直接复用现有 Node/Express 代理，改造范围和排错成本最低，因此作为第一版方案。

#### Electron + Electron Forge

能够实现相同的桌面能力，但现有项目接入和安装包定制路径不如 electron-builder 直观。除非后续明确采用 Forge 的发布流程，否则不选用。

#### Tauri

安装包和资源占用更小，但需要用 Rust 重写或重新封装代理服务，无法自然复用 Express 代理。第一版不以最小体积为优先，因此不选用。

## 4. 目录与组件

目录划分如下：

```text
web/oun/
├── desktop/                 # Electron 主进程、preload、图标和打包配置
├── docs/superpowers/specs/  # 设计与实现规格
├── src/                     # React/Vite 前端
├── dist/                    # 前端生产构建产物
└── proxy-server.js          # 可被桌面主进程调用的代理逻辑
```

主要组件职责：

- Electron 主进程：创建主窗口、注册单实例锁、启动和停止代理、创建托盘、处理退出和外部链接。
- Preload：在 `contextIsolation` 环境下，仅向渲染层暴露代理地址等必要的窄接口。
- React 渲染层：继续负责页面、搜索、播放、历史记录和响应式布局；通过可配置的代理地址访问本地代理。
- 代理模块：保留现有 Express 转发行为，将服务改造为可由 Electron 主进程启动并返回实际监听端口的模块。
- electron-builder：将前端构建产物、桌面代码和代理代码打入应用资源，输出 macOS 和 Windows 安装包。

## 5. 启动与数据流

1. Electron 启动并取得单实例锁。
2. 主进程在 `127.0.0.1` 上申请随机可用端口。
3. 主进程启动内置代理并等待服务监听成功。
4. 代理成功后创建窗口，使用 `loadFile` 加载内置的 `dist/index.html`。
5. Preload 向前端提供本地代理地址，例如 `http://127.0.0.1:49152`。
6. React 前端将现有 `/proxy?url=...` 请求改为请求可配置的本地代理地址。
7. 本地代理访问远程视频源接口并把响应返回给渲染层。
8. Artplayer 和 `hls.js` 继续处理 HLS/MP4 播放；可以直连的媒体 URL 保持现有直连行为，需要跨域代理的资源通过本地代理访问。
9. 搜索历史和视频源配置继续使用页面环境的 `localStorage`，第一版不迁移到原生数据库。

开发环境应继续支持现有 Vite 开发服务器和代理路径；生产桌面环境使用 Electron 注入的本地代理地址。两种环境应共享同一套前端请求抽象，避免为桌面端复制业务逻辑。

## 6. 安全边界

- 代理只监听 `127.0.0.1`，不暴露到局域网。
- 使用随机端口，避免固定端口冲突。
- BrowserWindow 设置 `contextIsolation: true`、`nodeIntegration: false`，并启用沙箱能力。
- Preload 仅暴露读取代理地址和必要状态的接口，不暴露任意文件系统、进程或命令执行能力。
- 阻止未知页面在应用窗口内导航；外部链接交由系统默认浏览器打开。
- 应用退出时关闭 HTTP 服务并释放端口，避免后台残留进程。
- 保持当前代理对既有视频源的兼容性；请求白名单、响应大小限制等加固措施只能在确认不破坏现有源的前提下增加。

## 7. 托盘与窗口行为

- 应用启动后显示主窗口，并创建系统托盘图标。
- macOS 和 Windows 点击窗口关闭按钮时隐藏窗口，不退出应用。
- 托盘菜单提供“显示主窗口”和“退出应用”。
- 选择“显示主窗口”时恢复窗口、显示并聚焦它。
- 选择“退出应用”时先停止代理服务，再销毁窗口、托盘和 Electron 进程。
- 第二次启动应用时不创建新实例，而是通知已有实例显示并聚焦主窗口。
- 使用平台对应的托盘图标资源，至少准备 `.icns` 和 `.ico`。

## 8. 错误处理

- 代理启动失败：不加载看似可用的窗口，显示明确错误对话框，提供“重试”和“退出”。
- 代理运行中意外退出：自动尝试重启一次；重启仍失败时通知窗口显示本地代理不可用，并提示重启应用。
- 远程视频源不可访问：沿用前端已有错误提示，不将远程网络错误误报为桌面应用故障。
- 前端无法连接本地代理：显示代理不可用提示，并保留重试路径。
- 应用退出和窗口销毁流程需要保证代理的关闭逻辑执行，避免留下孤立服务。

## 9. 构建与分发

建议新增桌面开发和构建脚本，明确区分以下阶段：

1. 安装根项目与前端依赖。
2. 构建 React/Vite 生产资源。
3. 编译或准备 Electron 主进程与 preload 代码。
4. 使用 electron-builder 打包前端 `dist`、桌面代码、代理模块和图标。
5. 生成 macOS `.dmg` 与 Windows `.exe` 安装包。

打包后的应用必须从内置资源加载前端，不依赖远程网站 URL，也不要求目标机器存在 Node.js。视频接口和媒体内容仍由应用运行时通过网络访问。

签名、公证和 Windows 代码签名不作为第一版功能范围，但构建配置应保留后续接入签名证书和发布流水线的空间。未签名构建可能在目标系统上出现安全提示，发布前需要单独处理平台签名与公证。

## 10. 验证策略

自动或脚本化验证：

- 前端生产构建成功。
- Electron 主进程和 preload 可被编译或加载。
- 代理可以启动、返回实际端口，并能转发有效请求。
- 代理启动失败、运行时退出和退出清理路径可测试。
- 单实例锁能唤醒已运行窗口。

手工验证：

- macOS 安装包生成、安装和启动。
- Windows 安装包生成、安装和启动；优先在 Windows 实机或 CI 中验证。
- 未安装 Node.js 的目标环境可以打开应用。
- 关闭窗口后应用仍驻留托盘，托盘可恢复窗口并能真正退出。
- 搜索、多源结果、视频源导入、历史记录、HLS 播放和 MP4 播放回归正常。
- 网络不可用和本地代理不可用时显示可理解的错误。

完成标准是：macOS 和 Windows 都能安装并启动内置前端；代理由应用自动管理；核心视频搜索和播放流程可用；窗口和托盘行为符合本规格；退出后没有残留代理进程。
